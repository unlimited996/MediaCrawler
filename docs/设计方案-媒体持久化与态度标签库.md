# 一、帖子图片丢失修复

## 1.1 现状排查（实测）

```
story 45《婆婆对我要离婚的态度》  status=active  chapter.source_url=.../explore/6ad3577d0000000015009380
  media 148~153（6 张）  local_path = None
  source_url = http://sns-webpic-qc.xhscdn.com/202610191658/<hash>/notes_pre_post/...
story 50《大家评评理🥺》        status=active  chapter.source_url=.../explore/6ac2482d000000000a01ca07
  media 155~158（4 张）  local_path = None
  source_url = http://sns-webpic-qc.xhscdn.com/202610201019/<hash>/notes_pre_post/...
```

- 直接 `curl -I` 其中一条外链 → **403**（签名过期 + 防盗链，浏览器直连必裂）。
- 两帖**原帖未被删除**（`story.status = active`），所以「原帖删除导致外链失效」在本例中不是主因，但它是最典型的失效场景之一，方案必须一并覆盖。
- 本地缓存**实际存在**：
  - `data/xhs/media/6ac2482d000000000a01ca07/001~004.webp`（4 张，10-20 10:28）
  - `data/xhs/media/6ad3577d0000000015009380/001~006.jpg`（6 张，10-19 18:11）
- 为什么没登记：`tools/v2_sync.py` 在**同步那一刻**用 `build_media_dir()/candidate.exists()` 探测本地文件；若同步先于下载落盘（或那次抓取未开 `--get_media`），`local_path` 就留空，之后**再也不会回补**——这是缺一个「回挂」环节，不是数据丢了。

## 1.2 修复方案：三层读取优先级 + 本地缓存回挂

### 读取优先级（前端 + 后端统一）

```
1. local_path  → /api/data/media/{platform}/{content_id}/{file}   （本地落盘，首选）
2. storage_key → 对象存储直链 / 后端代理                            （若启用 OSS/S3）
3. inline_data → data:image/...;base64                             （仅小图兜底，<256KB）
4. source_url  → /api/data/media-proxy?url=...                     （最后兜底，必带占位图）
```

前端 `shared.tsx::pickMedia()` 目前只取 `local_url || url`，需改为按上述顺序取，并且第 4 档渲染时挂 `onError → 占位图`，不允许出现破图图标。

### 立即修好这两帖：本地缓存回挂脚本

新增 `scripts/backfill_media_local.py`：

1. 遍历 `media_attachment` 中 `local_path IS NULL` 且 `target_type='chapter'` 的行；
2. 由 `target_id → story_chapter.source_content_id` 取到 `content_id`（平台原始 ID）；
3. `media_dir = build_media_dir(DATA_DIR, platform, content_id)`；
4. 按 `sort_order + 1` 生成 `001/002/...`，在 `.webp/.jpg/.jpeg/.png/.gif` 中找第一个存在的文件；
5. 命中即写 `local_path`、`download_status='done'`、`size_bytes`、`mime_type`、`storage_type='local'`、`ext.origin='local_cache'`；
6. 未命中不动（用户要求：本地没有就算了，不做网络补下载）。

> 幂等：只补 `local_path IS NULL` 的行，可反复跑。服务启动时也可挂一次（与 sentiment/stance 回填同款模式）。

### 原帖被删除 / 外链失效的兜底

- 后端新增**外链健康探测**（低频、可选）：对 `local_path IS NULL` 的媒体抽样 HEAD，403/404 则置 `source_status='dead'`；
- 详情页遇到 `source_status='dead'` 且无本地/对象副本 → 渲染「原图已失效」占位卡，而不是破图；
- `story.status='deleted'` 的场景：保留本地副本不动，只在 UI 上标注「原帖已删除，以下为最后快照」（现有逻辑已有此徽标）。

## 1.3 表结构 / 字段调整建议（增量，不改既有语义）

`media_attachment` 新增列（全部可空 / 有默认，老数据无需迁移）：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `storage_type` | varchar(16) default `'url'` | `local` / `object` / `inline` / `url` |
| `storage_key` | text | 对象存储的 object key（或相对路径），与 `storage_type` 配套 |
| `checksum` | varchar(64) | 内容 sha256，用于**去重**（同一张图重复抓取只存一份） |
| `source_status` | varchar(16) default `'unknown'` | `alive` / `dead` / `unknown`，外链健康度 |
| `source_checked_at` | timestamptz | 上次探测时间 |
| `downloaded_at` | timestamptz | 落盘完成时间 |
| `inline_data` | bytea（可空） | **仅** <256KB 的小图/头像兜底，大图禁止入库 |
| `inline_mime` | varchar(64) | 配合 `inline_data` |

索引：`idx_media_checksum(checksum)`（去重查询）、`idx_media_storage(storage_type, download_status)`；
保留既有唯一约束 `uq_media_src(target_type, target_id, source_url)` —— 它就是「只新增」的幂等锚点。

`story` 新增列（可选，便于列表页直接展示）：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `media_count` | int default 0 | 媒体数（列表页展示用，避免 join） |
| `cover_media_id` | bigint null | 封面指向某条 media（可选） |
| `edited_at` | bigint null | 最后一次检测到编辑的时间 |
| `edit_count` | int default 0 | 编辑次数（详情/列表角标） |

> 说明：大图一律**不编码进库**（PG 行会迅速膨胀、备份变慢）；「编码后存库」只作为对象存储不可用时的**小图兜底**（`inline_data`）。默认存储策略 = 本地 `DATA_DIR`，对象存储通过适配器可选开启（配置项 `MEDIA_STORAGE_BACKEND=local|s3`，不引新依赖也能跑）。

## 1.4 抓取策略：只新增，不删除

`tools/v2_sync.py` 的媒体同步改为 **upsert-by-`uq_media_src`**：

- 新 URL → INSERT（`download_status='pending'`，下载完成后置 `done` 并写 `local_path/checksum`）；
- 已存在 URL → 只 UPDATE 元数据（如补齐 `local_path`/`checksum`/尺寸），**不删**；
- 本次抓取结果里缺失的历史媒体 → **永不删除**（原站偶尔不返回全量图，删了就真没了）；
- 只有 `story` 硬删除（`_hard_delete_story`）才级联删除媒体行与磁盘文件（沿用现有语义）；
- 下载失败重试不覆盖已有成功记录（避免把 `done` 打回 `pending`）。

# 二、回复态度判断 → 可维护状态标签库

## 2.1 数据结构设计

### 表 `stance_tag`（标签定义）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | bigint PK | |
| `code` | varchar(32) unique | 稳定编码：`agree` / `neutral` / `oppose` / `sarcasm`(阴阳) / `speechless`(无语) / `doubt`(质疑) / `mock`(嘲讽) / `wait`(观望) / `god_comment`(神评) |

| `color` | varchar(16) | 徽标颜色（`#22c55e` 绿 / `#94a3b8` 灰 / `#f43f5e` 粉 …），前端不再硬编码 |

| `is_fallback` | bool default false | 是否为兜底标签（唯一，默认给 `neutral`） |
| `priority` | int default 100 | 命中冲突时的优先级（越小越先匹配） |
| `version` / `updated_at` | bigint / timestamptz | 变更版本，缓存失效用 |

### 表 `stance_tag_rule`（判定规则，与标签解耦）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | bigint PK | |
| `tag_id` | bigint FK(stance_tag.id, cascade) | |
| `pattern` | text | 匹配串或正则 |
| `match_type` | varchar(16) | `keyword`（子串） / `regex` / `sentiment`（情感映射） / `laughter`（纯笑声） / `mock`（嘲讽句式） |

| `negatable` | bool default true | 是否参与「否定词翻转」（如「不敢苟同」不该被反过来） |

### 表 `stance_tag_version`（缓存版本，单行）

| 字段 | 说明 |
| --- | --- |
| `id=1`, `version` bigint, `updated_at` | 任一标签/规则增删改 → `version += 1` |

### `comment` 表增列

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `stance_tag_id` | bigint null | 命中的标签（可空 = 未重算的老数据） |
| `stance_tag_code` | varchar(32) null | 冗余编码，列表/筛选/统计直接读，避免 join |
| `stance_confidence` | numeric(4,2) null | 置信度（可选展示） |

保留既有 `stance`（agree/neutral/oppose）作为**三态归并列**，由 `tag.polarity` 写入，赞同度计算继续用它，改动面最小、可灰度回滚。

## 2.2 存储方式与「改完立即生效」

- 持久化：PG（v2 库），与业务同库同会话约定（复用 `tools/v2_sync._v2_session`）。
- 进程内缓存：`StanceTagStore` 单例持有 `{version, tags[], rules[]}`；
- 失效机制：每次判定前比对 `stance_tag_version.version`（一次轻量查询，可 30s 本地 TTL），不一致立即重载；管理端改完也会主动调 `/api/stance-tags/refresh` 广播（单实例场景够用；多实例靠 TTL 兜底）。
- **不硬编码**：`tools/stance.py` 里现有的 `_AGREE_DIRECT` / `_OPPOSE_DIRECT` / `_MOCK_OPPOSE` / `_OFFTOPIC_MARKERS` 全部转成**内置种子数据**，首次启动（`api/main.py` startup）写入库；种子只在表为空时写入，之后以库为准。

## 2.3 判定流程与兜底

```
judge_comment_stance(text, post_stance):
  1. 读最新标签库（版本比对 → 命中缓存或重载）
  2. 空文本 → 兜底标签
  3. 按 priority 升序遍历 enabled 标签的 enabled 规则：
       keyword  → pattern in text（可考虑 negatable 的否定前置翻转）
       regex    → re.search
       sentiment→ 情感极性 × 帖子立场映射（沿用现有映射表）
       laughter → 剔除笑声/表情后无实质内容
     命中即返回 (tag_code, tag_id, confidence)
  4. 一条都没命中 → 返回 is_fallback=true 的标签（默认 neutral），
     confidence=0.3，reason='fallback'
```

- 兜底标签由库指定（`is_fallback` 唯一约束用部分唯一索引保证），改一个配置即可换兜底，不动代码。
- 冲突：`priority` 小的优先；同优先级取 `weight` 高的。

# 三、实施顺序（建议）

| 阶段 | 内容 | 产出 |
| --- | --- | --- |
| P0 | `scripts/backfill_media_local.py` + 前端四档读取优先级 + 占位图 | 两帖图片立刻恢复 |
| P1 | `media_attachment` 增列 + v2_sync 媒体 upsert（只新增不删除）+ 本地/对象存储适配开关 | 后续抓取不再依赖外链 |
| P2 | `story_edit_log` + 编辑检测 + `/edits` 接口 + 详情页编辑记录弹层 | 可查看/比对前后差异 |
| P3 | 标签库三张表 + `stance.py` 重构 + CRUD API + 内置 9 个标签种子 + 迁移脚本 | 判定逻辑与代码解耦 |
| P4 | 状态库管理页 + 评论区筛选/徽标动态化 + rejudge | 运营可自助维护 |

风险与注意：
- 对象存储为可选项，**默认本地**，避免引入新依赖影响 Docker 构建；
- 大图禁止 `inline_data` 入库；
- 重算（`rejudge`）是全表更新，需分批 + 限流，避免长事务；
- 媒体去重（`checksum`）会跨 story 命中同一张图，删除 story 时不能删掉仍被引用的文件（引用计数 or 只删行不删文件）。
